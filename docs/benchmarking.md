# Benchmark methodology

The Python benchmark reports session initialization, first inference, and warm distributions for a fixed default input. It measures batches 1, 8, 32, and 128 with configurable warmup, measured iterations, and independent fresh sessions (three by default). The browser worker reports manifest/schema/model fetch and hash durations, ONNX session/WASM setup, first inference, time to first usable prediction, asset sizes, and warm batch distributions. Browser benchmarks create three fresh ONNX sessions by default. Each sample times a block of 20 real inferences and divides elapsed time by 20 because one small-model execution can be below `performance.now()` timer resolution. The report records the repetition count and retains per-session results as well as pooled measurements. These are per-execution averages, with block-level percentiles.

These are local descriptive measurements. Browser engine, cache state, thermal state, operating system, hardware, and runtime build affect latency. Measurements from different computers are not a controlled runtime bake-off. Browser navigation timing and encoded asset transfer sizes are recorded when exposed, but the project does not currently run controlled cold-versus-warm cache experiments or measure Python process startup separately. Independent sessions are initialized in one process or worker context, so they do not measure process or browser startup. Tiny model compute can be smaller than startup overhead. Do not compare a Python cold start with browser warm latency.
